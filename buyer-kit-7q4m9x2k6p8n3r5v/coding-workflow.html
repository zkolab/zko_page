PRACTICAL WORKFLOW

编程工作流心得

AI 编程不是把一句模糊需求扔进去等结果。更稳的做法是让合适的 Skill 在合适的阶段接手：先澄清、再计划、再实现、出错就系统排查，最后拿验证证据。

开始第一次开发任务按领域选 Skill
记住这条主线
  • 先读项目，不急着改
  • 新功能先 Brainstorming
  • 失败先 Systematic Debugging
  • 没有验证证据不说完成

FIRST PROJECT

第一次开发任务：给网页加一个小功能

下面流程适合 Codex、Claude Code、Cursor 等能读取项目的工具。目标不是一次做大项目，而是让你掌握一套可重复的安全节奏。

  1. 1

    打开正确的项目目录

    不要在桌面根目录或包含私人资料的大文件夹启动 Agent。

    请只读查看当前目录，不要修改文件。告诉我这里是否是一个项目，以及最重要的说明文件在哪里。

    你需要确认：目录里只有本次项目需要的文件，没有私人资料。

    成功标志：AI 引用的文件真实存在。

    下一步：让 AI 阅读项目说明和规则。

  2. 2

    让 AI 先读说明

    要求它阅读 README.md、AGENTS.md 和与任务相关的文件。

    请阅读 README.md、AGENTS.md 和与页面相关的文件。用简单中文说明运行方式、测试命令和必须遵守的项目规则，暂时不要修改。

    你需要确认：它找到的启动和测试命令与你看到的说明一致。

    成功标志：它能说出真实的启动命令、检查命令和项目规则。

    下一步：用 Brainstorming 明确这次只做什么。

  3. 3

    使用 Brainstorming 明确需求

    新功能、页面改版和行为变化都先讨论成功标准。

    $superpowers:brainstorming 请帮我设计一个“回到顶部”按钮。面向手机用户，保持现有视觉风格，不增加第三方库。

    你需要确认：按钮何时出现、放在哪里、怎样算完成。

    成功标志：设计写清目标、边界和验收标准，并得到你的确认。

    下一步：把批准的设计拆成实施计划。

  4. 4

    使用 Writing Plans 拆步骤

    设计确认后，让 AI 写出文件、测试和验证步骤。

    $superpowers:writing-plans 根据已批准的设计创建实施计划，列出准确文件、失败测试、最小实现、验证命令和提交步骤。

    你需要确认：计划没有加入你未批准的大改动或新依赖。

    成功标志：每一步都有准确文件、预期结果和验证命令。

    下一步：从第一个失败测试开始实现。

  5. 5

    先写失败测试再实现

    使用 Test-Driven Development，让测试先证明功能尚不存在。

    $superpowers:test-driven-development 按计划实现第一个任务。先写一个会因功能缺失而失败的测试，展示失败原因后再写最小实现。

    你需要确认：测试确实因为功能缺失而失败，不是路径或语法写错。

    成功标志：先看到预期 RED，再看到最小实现后的 GREEN。

    下一步：继续下一个小步骤；出现异常就停止猜测并调试。

  6. 6

    失败时使用 Systematic Debugging

    不要不停换命令碰运气，先收集现象和定位根因。

    $superpowers:systematic-debugging 当前测试失败。请先复现、读取完整错误、提出根因假设并用最小检查验证，不要直接大范围改代码。

    你需要确认：AI 展示了完整错误和能验证根因的证据。

    成功标志：修改针对已验证的原因，修复后原失败测试通过。

    下一步：回到实施流程并完成剩余步骤。

  7. 7

    完成前使用 Verification Before Completion

    让 AI 重新运行完整命令，并根据最新输出汇报。

    $superpowers:verification-before-completion 请重新运行相关测试和检查，读取完整输出后再判断是否完成；列出通过数量、失败数量和仍有限制。

    你需要确认：命令是刚刚实际运行的完整验收命令。

    成功标志：汇报包含通过数、失败数和仍有限制，关键检查为零失败。

    下一步：检查 Git 改动并请求代码审查。

  8. 8

    审查改动并完成分支

    确认只改了相关文件，再处理审查意见和保存 Git 版本。

    $superpowers:requesting-code-review 请根据批准的需求审查本次改动，优先报告会导致功能错误、安全问题或回归的具体问题。

    你需要确认：重要审查意见已经逐条验证、修复或用证据说明不适用。

    成功标志：工作区没有意外文件，测试仍通过，提交内容只包含本次任务。

    下一步：使用 Finishing a Development Branch 选择合并、PR 或保留分支。

DEVELOPMENT SKILLS

Superpowers：按阶段调用，不要全部一起叫

Superpowers 是一组开发流程 Skills。你只需要记住当前在哪个阶段，然后调用对应 Skill。

需求阶段

Brainstorming

什么时候用：增加功能、改页面、改变行为之前。

怎么调用：$superpowers:brainstorming

你要提供：目标用户、想实现的结果和限制。

下一步：批准设计后进入 Writing Plans。

计划阶段

Writing Plans

什么时候用：设计已经确定，准备改代码。

怎么调用：$superpowers:writing-plans

你要提供：批准的设计或明确需求。

下一步：按计划逐任务实施。

实现阶段

Test-Driven Development

什么时候用：实现功能或修复缺陷。

怎么调用：$superpowers:test-driven-development

你要提供：可观察的成功行为。

下一步：先看 RED，再实现 GREEN。

故障阶段

Systematic Debugging

什么时候用：测试失败、程序异常或结果不符合预期。

怎么调用：$superpowers:systematic-debugging

你要提供：完整报错、复现步骤和最近改动。

下一步：验证根因后才修复。

审查阶段

Requesting Code Review

什么时候用：重要功能完成、合并前。

怎么调用：$superpowers:requesting-code-review

你要提供：需求、改动范围和验证结果。

下一步：按严重程度处理真实问题。

审查阶段

Receiving Code Review

什么时候用：收到审查意见，准备判断是否应该修改。

怎么调用：$superpowers:receiving-code-review

你要提供：完整评论、对应文件和当前测试证据。

下一步：先验证意见是否适用于当前项目，再逐项修复和测试。

收尾阶段

Verification Before Completion

什么时候用：准备说“完成、修好、通过”之前。

怎么调用：$superpowers:verification-before-completion

你要提供：验收命令和成功标准。

下一步：有最新证据后再交付。

合并阶段

Finishing a Development Branch

什么时候用：测试通过，准备合并、创建 PR 或保留分支。

怎么调用：$superpowers:finishing-a-development-branch

你要提供：目标基础分支和希望采用的收尾方式。

下一步：合并后重新测试，再清理已完成的临时工作树。

在 Codex 中怎样找到 Skills：

  • /skills：查看或选择当前可用 Skills。
  • $skill-name：明确调用某个 Skill。
  • $skill-installer：安装精选 Skill 或从仓库安装 Skill。

MORE THAN CODE

按不同领域选择 Skills

Skill 是针对一种任务的可复用工作流程。名称可能随安装包变化，使用前先在 Skills 列表中确认。

Word文档

Documents

什么时候用：创建或修改 DOCX、红线修订、排版检查。

调用方式：明确说“使用 Documents Skill 创建一份 Word 文档”。

你要提供：内容、受众、页面格式和参考文件。

下一步：要求渲染页面并检查版式。

PDF表单

PDF

什么时候用：读取、制作、合并、检查 PDF 或填写表单。

调用方式：明确文件路径和最终输出。

你要提供：页面尺寸、是否需要打印和表单字段。

下一步：要求逐页渲染检查。

Excel数据

Spreadsheets

什么时候用：创建 XLSX/CSV、公式、表格分析和数据清洗。

调用方式：说明输入文件、所需列和计算规则。

你要提供：示例数据和预期结果。

下一步：检查公式、数值和工作表布局。

PPT演示

Presentations

什么时候用：制作或修改 PowerPoint、讲稿和版式。

调用方式：说明页数、受众、风格和现有模板。

你要提供：核心信息和参考资料。

下一步：渲染所有幻灯片检查溢出。

图片创意

ImageGen

什么时候用：生成照片、插图、纹理、透明背景图。

调用方式：描述主体、构图、风格、比例和用途。

你要提供：品牌限制和参考图。

下一步：检查尺寸、文字错误和版权风险。

图表交互

Visualize

什么时候用：图表、对比、流程图、模拟器和交互解释。

调用方式：说明数据、需要看懂的关系和交互控件。

你要提供：准确数字或计算规则。

下一步：验证图中数据与原始来源一致。

网页测试

Browser Control

什么时候用：打开网页、检查界面、填写测试表单或验证本地网站。

调用方式：给出网址和允许的操作范围。

你要提供：登录要求和不能提交的内容。

下一步：让 AI 截取状态或报告可验证结果。

安装制作

Skill Installer / Skill Creator

什么时候用：安装别人维护的 Skill，或把自己的重复流程做成 Skill。

调用方式：$skill-installer 或 $skill-creator。

你要提供：来源仓库、触发条件和工作流程。

下一步：使用一个真实任务验证是否正确触发。

ZKO WORKFLOW

把语音、手柄、AutoClipboard 和 Agent 串起来

  1. 1

    说出任务

    使用 OpenLess、Typeless 或系统语音输入，把需求说进 AI 工具。

  2. 2

    按宏键确认或发送

    将一个按键配置为语音快捷键或粘贴，另一个保留 Enter；先在记事本测试。

  3. 3

    观察 Agent 状态

    AutoClipboard 保持运行并完成 Agent 状态连接后，手柄灯环或小屏显示工作中、等待授权、完成或阻塞。

  4. 4

    需要授权时再操作

    看到等待授权，不要盲目确认。先看 AI 准备执行的命令、文件和影响范围。

  5. 5

    继续下一条指令

    任务完成后，用语音补充要求，再用宏键粘贴、确认或发送。

基础蓝牙宏不依赖 AutoClipboard。即使软件未连接，手柄仍可发送已配置快捷键；Agent 状态、Profile 快开和深度联动才需要 AutoClipboard 保持运行。

COMMON MISTAKES

工作流常见问题

AI 一上来就改很多文件
中止任务，先让它列出计划、影响文件和测试方法。把任务缩小成一个可验证结果，再重新开始。
不知道该调用哪个 Skill
需求不清用 Brainstorming；需求清楚但步骤多用 Writing Plans；实现功能用 TDD；遇到失败用 Systematic Debugging；准备交付用 Verification。
Skill 没有自动触发
先用 /skills 确认它存在，再在提示词中使用完整的 $skill-name 明确调用。新安装后仍看不到时，按官方说明刷新或重启 Codex。
AI 说完成了，但我不确定
要求它重新运行验收命令并报告通过数、失败数和完整错误。没有最新执行证据，就只把它当作“可能完成”。
